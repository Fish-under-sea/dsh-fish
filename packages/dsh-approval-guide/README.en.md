## What Problem Does This Solve

The approval dialog already ships some Chinese UI strings ("等待审批", "拒绝", "允许一次"), but **the approval reason generated by the host is English-only**. The most common one looks like this:

```text
escalate sandbox to danger-full-access: <one-line English reason from the model>
```

The reader has to judge on their own what the command will actually do, how much it will unlock, and what the consequences are — and the English-only template raises that cost. This plugin injects a tiered Chinese explanation below the reason and the command, covering "what it will do / what the risks are / on what basis".

## Result

The detail area inside the approval card becomes:

```text
<original command>

What this approval will do
Escalate the file sandbox scope of this pwsh call to "fully open" (danger-full-access).
Effective only for this single call: no long-lived grant, no effect on later commands.
Risk
Once opened, this command is no longer confined by the workspace boundary: it can read
and write any file on the host, including system directories, other projects, SSH keys,
and credential files, and this execution no longer asks for your approval item by item.
Only allow it if you fully trust this command.
  · Tool: pwsh
  · Target permission: fully open (danger-full-access)
  · Reason given by the model: <original text>
When in doubt, click "Reject" first: rejecting does not interrupt the conversation;
I can retry later with read-only or workspace-write instead.
```

The explanation is always shown in Chinese and does not follow the UI language — switching the interface to English still leaves the Chinese prompt in place.

### Tiered Copy

The Chinese explanation is produced by **static rules**: no extra model call, no API quota consumed, and it cannot be swayed by the requester's own wording.

| Target permission | Level | Key points of the risk copy |
| --- | --- | --- |
| `danger-full-access` | High (red title) | No longer confined by the workspace boundary; can read and write any file on the host (including system directories, other projects, SSH keys, and credential files); this execution no longer asks for approval item by item. |
| `workspace-write` | Caution | Can write to the current workspace directory and its subdirectories, plus the system temp directory; still cannot write outside the workspace. |
| Other modes | Caution | Not a built-in DSH mode — no precise scope can be given; prompts that the command will run at the requested permission. |
| No sandbox parameter | Caution | Generic fallback: the tool requests a higher permission for this single operation, effective only this time. |

## Installation

```sh
# Install from npm (recommended)
dsh plugin --profile <profile> add @fish-under-sea/dsh-approval-guide
```

`--profile` should be followed by the actual profile name on your machine: `desktop` for the desktop app, `web` for the web app.

Use `link:` to point at this directory only when you need to modify the source (the repo source is the install source — restart DSH after changes for them to take effect):

```sh
dsh plugin --profile <profile> add "link:<absolute path to this directory>"
```

After installation, you need to **restart the DSH app and refresh the page** for it to take effect (the web build has no in-place restart).

### Uninstallation

```sh
dsh plugin --profile <profile> remove @fish-under-sea/dsh-approval-guide
```

### Post-Install Self-Check

```sh
dsh --profile <profile> --dump-config
```

The end of the output should contain exactly one `- id: approval-guide` / `name: @fish-under-sea/dsh-approval-guide` entry. Multiple entries mean the plugin is mounted more than once, and the app will fail to start.

## Usage

No configuration is needed after installation — the plugin automatically occupies the `conversation.approval.detail` slot of the approval detail area and appends the Chinese explanation to every approval prompt.

The explanation is resolved in a defense-in-depth order: first read the tool-call arguments `sandbox_permissions` / `justification`; if those are unavailable, parse the host reason template (`escalate sandbox to <mode>: <reason>`); if that also fails, fall back to the generic explanation. Even when every layer fails to produce a value, a generic Chinese explanation is still shown.

Coverage:

- All interactive approvals **with a correlated tool call**: sandbox permission escalation, asks triggered by hooks, and asks initiated by other plugins through the approval channel.

## Configuration

**No configuration file.** This package has no configuration options and does not read or write any settings file — all rules are hardcoded in `lib/client.js`.

## Compatibility and Boundaries

- Platform: pure browser plugin (`dsh.client.platform: web`); the host half is an empty implementation.
- Occupies the `conversation.approval.detail` sub-slot of the core package `@deepseek-ai/dsh-client-ui-approval`. The slot is of `single` type, sorted by priority in **ascending order** with the **smallest number rendered**; the official occupier `ApprovalCommand` uses the default priority 0, and this plugin registers with `priority: -1` to override it, while re-rendering the original command inside the component using the same logic (`useChat` to fetch the correlated tool call, parsing `argsRaw.command`) so no information is lost.
- When the component throws, the slot renderer reclaims the entry (abdicate), and the official `ApprovalCommand` automatically resumes rendering — the approval card never goes blank, and the approval flow is never blocked.
- Compatible with both generations of selectors: DSH 0.2.0 (`useSessionStatus`) and 0.1.x (`useSessionPendingInteraction`).

Data sources:

| Data | Source |
| --- | --- |
| Command and arguments of the correlated tool call | `useChat` selector (same as the official `ApprovalCommand`) |
| Tool name and approval reason | `useSessionPendingInteraction` / `useSessionStatus` selector (pending interaction with `kind === 'approval'`) |

### Known Limitations

- If an approval request has **no correlated tool call** (missing `callId`), the core does not render the detail area, and this plugin has nowhere to insert. This is dictated by the core slot contract and cannot be worked around by this plugin.
- The Chinese explanation describes the risk at the "permission scope" layer; it does not judge whether the command itself is safe. You still need to read the command yourself.
- If the host changes the reason template (`escalate sandbox to <mode>: <reason>`), the first-layer argument lookup still works; only the second-layer fallback would stop working.

## Development and Testing

```sh
node packages/dsh-approval-guide/test/guide.test.mjs
```

All 12 cases currently pass. The test loads the actual `lib/client.js` that goes into the browser: it uses `node:vm` to provide `window.__ModuleLoader__`, captures the factory registered by the bundle, instantiates it with a fake module table, and directly asserts on the element tree produced by the pure functions and the component. **Zero dependencies** — no need to install React or vitest.

> Do not use `node --test test/`: the test runner spawns child processes and captures their piped output, which fails with `EPERM` inside a restricted sandbox. Just run the test file directly.

Cases covered: tiered copy for the two sandbox modes, reason-template fallback parsing, unknown modes, generic approval fallback, corrupted argument JSON, no exception on empty input, component preserves the original command, degradation when pending interaction is unavailable, slot registration priority.

Directory layout:

| Path | Purpose |
| --- | --- |
| `lib/index.js` | Host half, empty implementation (pure browser plugin) |
| `lib/client.js` | Browser half: Chinese copy, tiering logic, approval detail component, slot registration |
| `cordis.patch.yml` | Bundle patch layer that inserts the plugin entry into the profile registry |
| `test/guide.test.mjs` | Zero-dependency tests |
