> **① `session-title-refresh` 0.3.2 — fixes "when the title model does not support the `off` rung, every auto-naming attempt fails with UNSUPPORTED_REASONING_EFFORT."** Symptom: `provider "hy-f" model "buddy/hy3" does not support reasoning effort "off"`, with title generation dead outright. The root cause was a defect introduced by the 0.3.1 fix itself: to cure "thinking eats the whole output budget" it sent `reasoningEffort: 'off'` **unconditionally**, but **DSH core hard-validates an explicit effort and never degrades it** (`dsh-llm`'s `resolveCallWithInfo` throws outright when the model does not declare the rung, and also throws for any explicit effort when the model carries no reasoning metadata at all), while `dsh-llm-pi-ai` **pins every undeclared rung to unsupported**. The comment on that 0.3.1 line claimed "channels that do not support the rung fall back to their own default instead of erroring" — **that claim was false**. Reproduced against the real configuration: **33 of 58 models** (gpt / claude / kimi / glm / hy3 / minimax / mimo and more) failed on every single naming attempt under 0.3.1. 0.3.2 now **probes before it speaks**: it calls `ctx.llm.resolveModelInfo()` (the same source the dispatch validation uses) to read the model's real rungs, sends `off` when thinking can be disabled, otherwise falls back to the **lowest** rung the model does support, and omits the field entirely when there is no reasoning metadata at all. Probe results are cached per provider/model, and a failed probe only falls back to omitting the field. One factual correction as well: `purpose: 'session-title'` is consumed **only** by the official `dsh-llm-deepseek` adapter — `dsh-llm-pi-ai` ignores it completely — so on a pi-ai route omitting the effort means letting thinking eat the budget, which is exactly why the explicit effort is required. Core 25 + host 25 + client 13 = **63** cases, all passing (6 new core + 5 new host regression cases).
>
> **② `dsh-agent-teams-fish` 0.4.2 — fixes "the captain avatar is always the DeepSeek one."** A captain switched to qwen / claude / glm kept showing the same avatar. The cause was not missing artwork (all 10 vendors' captain images shipped in-package long ago) but that the **client hard-coded the captain image** as the constant `team-lead-deepseek-v2.png`, referenced directly by all three render sites, never looking at which model actually led the team — so `team-lead-qwen-v2.png` and the other 9 were **permanently unreachable**. Deeper still, the host side recorded only `captainSessionId` in `team.json` (the captain is the owning session, not a member), so the **captain's model route was never stored at all** and the client had nothing to compute from. 0.4.2 writes `captainProvider` / `captainModel` at team creation, exposes them in the snapshot (live value wins, so switching models follows immediately), and has the client use the same vendor detection as members; an unknown vendor falls back to the packaged captain image. Legacy team records (without the fields) read as before, and artwork plus the degradation chain are untouched. artwork-role-match 30 → **34** cases, with 2 new `verify.mjs` gates whose effectiveness was proven by injecting the original defect.

> **0.7.1 (2026-10-10):** **Fixes "the eighth member cannot be installed"** — `dsh-our-free-model` is now published to the npm **official registry** (`2.0.0`), and this bundle's dependency on it changed from `github:Fish-under-sea/Our-Free-Mode-fish` to **`^2.0.0`**. Root cause: pnpm 11 **enables `blockExoticSubdeps` by default**, which **forbids git / file / link protocols in subdependencies**, so 0.7.0 failed with `ERR_PNPM_EXOTIC_SUBDEP` on any machine with default settings — the only way to install it was to have the user disable `blockExoticSubdeps`. A registry version does not trip that guard, so **no security setting has to be relaxed**. Zero functional change: the only difference between 0.7.0 and 0.6.11 was adding this member.
>
> Also updated: `dsh-our-free-model`'s `package.json` drops `private: true` (it only guards against accidental publishes and does not affect the manifest); this repository's `package.json` (0.7.0 → **0.7.1**, dependency → `^2.0.0`); and both READMEs (install notes, the `[NOT_FOUND]` mirror-sync list, version numbers).

> **0.7.0 (2026-10-10):** Adds an **eighth member** — `dsh-our-free-model` (fork of upstream [Ebony-Vinyl/dsh-our-free-model](https://github.com/Ebony-Vinyl/dsh-our-free-model), repository [Fish-under-sea/Our-Free-Mode-fish](https://github.com/Fish-under-sea/Our-Free-Mode-fish), dependency `github:Fish-under-sea/Our-Free-Mode-fish`). This fork adds a **"hide channel model groups" master switch**: the channel pack contributes 13 provider groups (CodeArts / CodeBuddy / Loomy / Raccoon / MiniMax / Gemini and more) to the model picker, where they mix with the providers you configured yourself and stretch it — turning the switch on collapses all 13 at once. **Display only, never routing**: gateway requests go through `resolveModelInfo()`, so hidden models keep working; the channel settings page's "show list" / "disable all" reads `listAllModels()`, also unaffected; off by default, so an upgrade never silently changes the list you see. The switch lives at Settings → Free models → Preferences (`hideChannelModels` in `our-free-model/settings.json`, already in the `git-sync` allowlist, restored across machines). Upstream contributor mode: 36/37 passing (`upgrade-ui` already failed before the change).

When upgrading to 0.7.0 you must therefore remove that package from the profile's `dsh.profile.bundles` (or move it from `dependencies` into `devDependencies`). This repository's existing convention already requires sub-packages in `devDependencies`; it matters most for the eighth member.

> **0.6.9 (2026-10-10):** `@fish-under-sea/dsh-session-title-refresh` **0.3.1** (dependency range `^0.3.0` → **`^0.3.1`**) — **fixes "every auto-naming attempt fails with max-tokens."** Symptom: auto-naming and manual refresh failed for every session, with the log showing `title model abnormal finish reason (max-tokens)` across the board. Three stacked root causes: (1) the title call **never disabled thinking** (the official provider forces `effort='off'` when `purpose === 'session-title'`, but this plugin's own auxiliary call missed that layer); (2) the default output budget was only **64** tokens, which a thinking title model's reasoning consumes outright; (3) the assembler treated finish reasons as **all-or-nothing** — any `finish !== 'stop'` threw and kept the old title, so "budget ceiling" was reported as "model failure." 0.3.1 fixes all three: the title call now passes `reasoningEffort: 'off'`; the default output budget goes 64 → **256**; and a `max-tokens` finish **accepts the truncated result when usable text was produced** (titles are short, so truncation usually only affects trailing punctuation or whitespace), failing only on an empty body. Core 19 + host 20 + client 13 = 52 cases, all passing (3 new regression cases: `reasoningEffort` must be sent, a `max-tokens` result with text must be accepted, and the default budget must be ≥ 256).

> **0.6.5 (2026-10-07):** `@fish-under-sea/dsh-visual-companion` **0.1.5** (dependency range `^0.1.4` → **`^0.1.5`**) — **Fixes crash where "auto-bind on load" marks the entire plugin as "abnormal."** Symptom: the plugin panel shows a red dot "abnormal," and the `visual_companion` tool and `/companion` command vanish together. Cause: when `<watchDir>/state` does not yet exist (fresh workspace, the companion service has not created this directory), `arm()` calls `fs.watch` on that path and **throws ENOENT synchronously** — on Windows, `fs.watch` on a non-existent path **throws** rather than emitting an `error` event, so the `.on('error')` handler right after it cannot catch it; the exception propagates to cordis's `apply()`, and the entry is marked "not activated." Now `mkdir -p` runs before binding, and a watch failure degrades to a warning with the status honestly left as "unbound" — **the plugin loads normally**, tool and command both present. `visual_companion({action:"arm"})` also now honestly returns "arm failed" on failure (previously it always returned "bound" regardless). Cases 8 → 10 (two new: directory missing → create and bind; path is not a directory → degrade to warning without crashing).
